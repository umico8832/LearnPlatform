# Agent 审查清单

本文档面向审查型 Agent。默认情况下，审查型 Agent 只读分析，不修改文件；只有用户明确要求修复、重构或落地修改时，才进入修改流程。

---

## 1. 审查前提

审查前应先确认：

- 用户要求的是代码审查、文档审查、变更复盘，还是判断能否 commit；
- 审查范围是当前工作区、某个 commit、某个 PR，还是仅基于用户描述；
- 是否已经读取真实代码和相关文档。

如果没有读取真实代码，只能说明“基于文档或用户描述判断”，不能假装完成代码级审查。

---

## 2. 重点检查项

审查时优先检查：

- 是否符合用户当前轮次的明确要求；
- 是否符合 `docs/product/roadmap.md` 中的当前项目阶段；
- 是否越界修改了无关文件或无关模块；
- 是否存在伪实现、硬编码、长期假数据或临时代码冒充完成；
- 是否弱化业务规则、权限规则、安全规则或数据一致性；
- 是否破坏 `docs/architecture/overview.md` 中的架构边界；
- 是否让大文件、大类、大组件继续膨胀，且没有合理拆分计划；
- 是否缺少必要测试或验证；
- 是否遗漏接口、数据库、架构、演示、简历等相关文档同步；
- 是否可以安全 commit。

涉及测试判断时，参考 `docs/development/testing.md`；涉及 Git 判断时，参考 `docs/development/git-rules.md`。

---

## 3. 输出结构

审查输出应区分：

- 必须马上改的问题：会导致功能错误、数据错误、安全风险、验收失败、构建失败或明显违背用户要求。
- 可以后续优化的问题：质量、结构、性能、可维护性方面的改进建议，但不阻塞当前目标。
- 不需要处理的问题：看起来可疑但结合项目阶段、范围或已有约定可以接受。

不要默认粘贴完整 diff。必要时引用文件路径和关键行号，重点说明问题、影响和建议处理方式。

---

## 4. 判断能否 Commit

判断能否 commit 时至少确认：

- 修改范围是否聚焦；
- 是否存在不应提交的文件；
- 必要测试或构建是否通过，未执行项是否有合理说明；
- 相关文档是否同步；
- commit message 是否符合 `docs/development/git-rules.md`；
- 提交是否按独立变更目的组织，复杂变更是否包含动机、关键边界、验证和兼容影响；
- 是否还有必须马上改的问题。

如果存在阻塞问题，应明确说“不建议 commit”，并列出最小修复项。
