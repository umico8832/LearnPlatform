# 工程规则

本文档为 LearnPlatform 的工程判断辅助清单，用于新增功能、修复问题、重构或判断代码归属时参考。它不替代 `docs/architecture/overview.md`、`docs/reference/api/index.md`、`docs/reference/database/index.md` 和 `docs/development/testing.md`。

---

## 1. 改动范围

- 默认采用工程保守模式：小步修改，聚焦当前目标，不做无关重构。
- 最小改动不等于持续往大文件、大类、大组件里堆代码；新增独立功能时应考虑合理归属。
- 如果发现现有模式不佳，可以记录建议或在总结中说明，不要顺手做大范围结构调整。
- 结构整理应单独成轮，不要和功能开发、Bug 修复混在一起。

---

## 2. 后端归属

后端应尽量遵循项目现有分层：

- Controller 负责请求入口、权限边界、参数接收和响应封装；
- Service 负责业务规则、事务边界和跨 Mapper 协作；
- Mapper 负责数据访问；
- DTO / VO 负责请求和响应数据结构；
- Entity 映射数据库表；
- Config / Security 负责配置、安全、过滤器等基础设施。

涉及判分、考试、权限、限流、AI 调用、缓存、文件上传、数据库一致性、事务或安全的改动时，需要更谨慎地确认业务约束，不能为了测试通过而弱化规则。

---

## 3. 前端归属

前端应尽量遵循项目现有分层：

- `views/` 放学习端页面级视图，`admin/views/` 放管理端页面级视图；
- `components/` 放可复用组件；
- `api/` 放接口请求封装；
- `stores/` 放跨页面状态；
- `router/` 放路由和守卫；
- `utils/` 放通用工具函数；
- `types/` 放 TypeScript 类型。

复杂页面不要无限膨胀。出现多个页面复用的展示、表单、状态转换或数据格式化逻辑时，应考虑抽到合适的组件、工具或类型文件中。

---

## 4. 跨层约束

- 前后端字段和枚举含义应保持一致。
- 新增依赖要说明原因，并优先使用项目已有技术栈和模式。
- 数据库字段命名使用 `snake_case`，Java / TypeScript 字段命名保持项目现有风格。
- 权限、判分、配额、审核状态和持久化结果以服务端事实为准。
- 接口、数据库和架构的权威来源分别见 `docs/reference/api/`、`docs/reference/database/` 和 `docs/architecture/`。

---

## 5. 敏感模块

以下模块改动需要额外谨慎，优先补充必要验证：

- AI 调用、流式输出、配额和调用日志；
- 统计、缓存、学习报告和图表数据；
- 考试、判分、错题归集、练习记录；
- 用户鉴权、角色权限、登录限流和验证码；
- 数据库迁移、逻辑删除、唯一约束和事务；
- 文件上传、导入导出；
- Docker、部署、监控、日志和 CI。

---

## 6. 仓库路径与生成物

- Git 跟踪路径必须能被 Java、Node.js、Docker 和常见跨平台工具稳定识别；文件名和目录名
  不使用 `< > : " | ? *`，也不以空格或句点结尾。
- `target`、`dist`、`node_modules`、测试报告、虚拟环境、缓存和系统垃圾文件不得提交。
- `python3 scripts/check-repository-layout.py` 是上述规则的自动门禁，并在 CI 文档任务中执行。
- 独立管理端的页面统一位于 `frontend/src/admin/views/`；门禁拒绝重新在
  `frontend/src/views/admin/` 下提交页面，避免两个应用边界再次混杂。
- 源文件必须使用构建工具能够识别的扩展名；禁止用异常路径保存一份不会被编译或测试发现的
  重复源码。
