# AI Agent 开发工作流

本文档是开发循环、任务验收、执行模式与完成状态的唯一规则来源。测试细则见[测试策略](testing.md)，
提交细则见[Git 规则](git-rules.md)，文档归属见[文档中心](../index.md#文档维护)。

---

## 1. 使用方式

按 [AGENTS.md](../../AGENTS.md) 读取当前状态与任务相关文档。本文件用于代码、配置、检查工具和协作规则修改。
纯文案或文档链接修正按[文档维护规则](../index.md#文档维护)验证，不必套用完整开发循环。

用户只给出简短需求时，Agent 应先从真实代码和项目状态补齐任务契约；能够安全推断的内容直接说明假设并继续，只有重大方向、破坏性操作或相互冲突的需求才暂停确认。

---

## 2. 任务 Prompt 模板

开始修改前，将任务整理为以下最小契约。不要为了填满模板而编造信息。

```text
目标：
- 本轮必须产生的用户可观察结果。

范围：
- 允许修改的模块、接口或页面。
- 明确不在本轮处理的相邻问题。

事实来源：
- 已读取的项目状态、设计文档和真实代码。
- 不能确认的信息与本轮采用的假设。

业务约束：
- 权限、判分、事务、数据一致性、安全、兼容性等不可弱化的规则。
- 涉及用户流程时接入真实前后端接口，不能把仅有后端或假数据页面视为业务闭环完成。

验收标准：
- 至少一个正常场景。
- 适用时包含边界、错误、权限或回归场景。

验证命令：
- 先执行的聚焦测试。
- 完成前执行的相关测试、构建和质量检查。

提交边界：
- 本批次达到哪个模块、阶段或业务闭环后才允许提交。
- 未达到边界时应继续开发或保留未提交改动，不以当前子任务结束代替完成。

停止条件：
- 需要新增权限、破坏兼容、执行数据清理或改变重大产品方向时暂停确认。
```

对简单、低风险任务可以压缩为几行，但目标、范围、验收标准、验证方式和提交边界不能缺失。

## 3. 标准开发循环

### 3.1 发现

1. 检查工作区，区分用户已有改动和本轮改动。
2. 阅读 `AGENTS.md` 指定的基础文档和任务类型文档。
3. 搜索现有实现、测试和相似模式，不重复创建已有能力。
4. 根据真实代码确定最小改动范围，不能只依据文档声称。

### 3.2 契约

1. 写清输入、输出、权限、状态变化和错误语义。
2. 接口或数据库变化先核对对应设计文档。
3. 将相邻优化列为非本轮范围；若当前结构已妨碍安全实现，再单独安排结构整理。

### 3.3 Red

符合 `docs/development/testing.md`“必须新增测试”的行为改动，先增加或修改一个能够失败的聚焦测试：

1. 测试应描述用户可观察行为或业务约束，不绑定无关实现细节。
2. 运行该测试并确认失败原因与目标一致；编译错误、夹具错误或环境故障不算有效 Red。
3. 修复缺陷时，优先用能够复现缺陷的回归测试形成 Red。

如果无法可靠制造 Red，例如纯配置兼容、仅删除死代码或必须依赖不可用的外部环境，应在开发记录中说明原因和替代验证，不能声称执行了 TDD。

### 3.4 Green

1. 只实现让目标测试通过所需的最小完整方案。
2. 不用硬编码、绕过权限、弱化校验或吞掉异常换取绿灯。
3. 先运行聚焦测试，再运行受影响模块的相关测试。

### 3.5 Refactor

测试保持绿色后再整理结构：

1. 删除重复逻辑，使用现有分层和命名约定。
2. 如果修改让大 Service、Controller 或 Vue 页面继续明显膨胀，应检查能否提取独立职责；不能合理拆分时在总结中说明原因。
3. 不在功能提交中夹带与目标无关的大范围重构。
4. 重构后再次运行聚焦测试。

### 3.6 Verify

按[测试策略](testing.md#2-分层验证l1--l2--l3)选择验证层级与范围；已通过且未受后续改动影响的验证
不重复执行。测试先行的适用行为、例外、工程单位和覆盖率规则均由测试策略维护。

涉及 Docker 构建、启动或清理前，读取[Docker 磁盘治理](docker-disk-governance.md)确定范围和授权。

### 3.7 Deliver

1. 检查 diff 是否只包含本轮范围。
2. 按[文档维护规则](../index.md#文档维护)更新实际受影响的权威文档与历史记录。
3. 按 `docs/development/review-checklist.md` 自审。
4. 对照任务契约与[Git 提交边界](git-rules.md#1-基本原则)，满足条件后创建聚焦本地提交；远端操作另行核对已有授权。
5. 区分任务完成与代码交付状态，按第 7 节汇报相关结果。

## 4. TDD 适用边界

哪些行为必须测试先行、哪些修改通常不新增测试，以及无法形成有效 Red 时的处理，统一见
[测试策略](testing.md#5-必须新增测试的情况)。第 3 节只描述适用时如何执行 Red、Green 和 Refactor，
不要求纯样式、文档或无行为机械修改制造失败测试。

---

## 5. 完成状态

任务是否完成与代码交付状态分开判断。完成当前授权目标、满足约定验收且没有必需工作遗漏，
可以报告“本地任务完成”；这不代表已经推送或远端 CI 通过。只读问答与审查不使用代码交付状态。

| 状态 | 必须满足的条件 | 报告边界 |
|---|---|---|
| IMPLEMENTED | 修改已实现，相称的聚焦验证通过 | 仍有模块验收或必要验证未完成，不称为完整验证或交付。 |
| LOCALLY_VERIFIED | 达到预定任务或模块验收边界，相称的 L2 / L3 本地验证通过；纯文档采用文档验证 | 可报告授权的本地任务完成；未验证远端 CI 时明确说明。 |
| DELIVERED | 达到提交边界，本地提交已创建，已获授权并完成推送，对应远端 CI 成功 | 可报告远端交付完成。 |

未授权 push 时，代码交付状态最高为 LOCALLY_VERIFIED，不得为了提升状态自行执行远端操作。
提交边界与保留未提交修改的条件遵循 [Git 规则](git-rules.md)。

### CI failure 的处理

如果用户已经授权 push，且 push 后 CI 失败，CI failure 自动成为最高优先级任务：
定位 → 修复 → 聚焦验证 → 必要 commit → push → 检查 CI，恢复 Green 后才继续新的
业务开发。不得在 CI 红的情况下把它写进遗留问题后继续开发下一 Feature，除非已可靠
确认 CI failure 与仓库代码无关（外部基础设施故障且无法通过仓库修改解决），此时必须
明确记录事实和证据。

## 6. 执行模式与阶段边界

### NORMAL / CONTINUOUS

- NORMAL 是默认模式：完成用户当前明确任务或达到当前 Phase Exit Criteria 后停止，
  输出总结，等待用户决定下一步。不得因为 status 还有“下一步”、roadmap 还有后续
  Phase 或发现了其他有价值优化就自行继续编码。
- CONTINUOUS 只有在用户明确表达持续开发意图时进入（例如“持续开发”“一直开发直到
  我叫停”“接下来你自主持续开发”）。Agent 不得自行从 NORMAL 切换到 CONTINUOUS，
  也不得因为一次回复结束、context compact、一个 commit 完成或一个 Phase 完成而把
  CONTINUOUS 改回 NORMAL。
- 用户明确暂停（“暂停”“停一下”“等我确认再继续”等）后回到 NORMAL。

当前 Execution Mode 记录在 [status](../project/status.md) 的“Agent 执行状态”，只有用户明确改变模式时
才能更新该值。模式不扩大授权范围；当前具体要求优先，不能因为保存了 CONTINUOUS 而跳过只读审查
或继续与当前要求无关的开发。

### CONTINUOUS 的推进路径

项目目标 → 当前 Phase → Remaining Required → Exit Criteria → Phase Exit → 下一明确
Phase → 继续开发。下一任务选择顺序：基线阻断问题（编译失败、必要测试失败、CI
failure、迁移失败、关键 E2E 回归）→ 当前 Phase Remaining Required → 当前 Phase
Exit → roadmap / PRD 已明确的下一 Phase。

### Phase 必须保持有限边界

每个当前 Phase 维护 Goal、Exit Criteria、Remaining Required、Backlog / Follow-up
和 Stop Condition。Exit Criteria 必须数量有限、可客观判断、与阶段核心目标直接相关，
不因为开发中发现的新优化而自动增加。只记录真正阻止 Phase Exit 的工作为 Required；
有价值但不阻止完成的增强（更多筛选、更多统计、对称入口、UI 小优化、内容扩张、
非必要重构）进入 Backlog。Exit Criteria 全部满足后当前 Phase 必须结束，不能因为
还能继续优化就继续往当前 Phase 加 Required。

### 持续维护的边界

维护工作没有新的产品 Phase 时，在 status 中记录当前问题清单、授权范围、验收标准和停止条件，
每项问题应有可核对的证据。按已授权范围处理下一明确问题，不因发现可优化之处而自动增加必做项。
当前清单完成且没有下一项已明确的工作时，报告结果并停止；保持执行模式值，不自行扩展维护范围。

### 硬停止条件

即使处于 CONTINUOUS，以下情况也必须暂停询问用户：

- 需要改变重大产品方向；
- roadmap 没有明确下一阶段且存在多个本质不同的大方向；
- PRD / roadmap / Exit Criteria 出现重大冲突；
- 需要删除或不可逆修改用户数据；
- 需要执行当前没有用户授权的 push、force push、rebase、reset、删除 branch / tag；
- 需要引入明显改变项目架构的大型基础设施；
- 需要制造破坏性公共 API / 数据兼容变化且没有既定迁移方案；
- 用户要求暂停。

局部重构、技术实现选择、必要测试、bug 修复、小型 API 内部调整和文档同步不属于硬停止条件。

## 7. 交付汇报

有修改的任务在结束时说明结果、主要修改文件、相关验证与未执行项、剩余必需工作和提交/推送/CI 状态；
下一步只列真实需要继续处理的事项，不为了填满模板创造任务。高风险改动应说明有效 Red/Green 或合理例外。

汇报前按[审查清单](review-checklist.md)核对业务闭环、权限与事实真实性、模块边界、必要文档和验证证据。
未达到验收或提交边界时，明确报告剩余范围；不能用风险说明替代高风险行为的必要验证。
纯文档不要求 Red/Green，只有相关验证；只读问答和审查直接回答结论与证据，不套开发交付模板。
