# AI Agent 开发工作流

本文档把项目现有的上下文读取、工程约束、测试策略和提交规则整理为一套可重复执行的 AI 开发协议。目标是减少上下文丢失、无关改动、重复实现和缺少回归保护，而不是依赖一条“万能 Prompt”。

---

## 1. 使用方式

新 Agent 仍应先按 `AGENTS.md` 读取基础文档。本文件用于新增功能、修复缺陷、重构或其他会改变代码行为的任务。

用户只给出简短需求时，Agent 应先从真实代码和项目状态补齐任务契约；能够安全推断的内容直接说明假设并继续，只有重大方向、破坏性操作或相互冲突的需求才暂停确认。

---

## 2. 任务 Prompt 模板

开始修改前，将任务整理为以下最小契约。不要为了填满模板而编造信息。

```text
目标：
- 本轮必须产生的用户可观察结果。

范围：
- 允许修改的模块、接口或页面。
- 明确不在本轮处理的相邻问题。

事实来源：
- 已读取的项目状态、设计文档和真实代码。
- 不能确认的信息与本轮采用的假设。

业务约束：
- 权限、判分、事务、数据一致性、安全、兼容性等不可弱化的规则。

验收标准：
- 至少一个正常场景。
- 适用时包含边界、错误、权限或回归场景。

验证命令：
- 先执行的聚焦测试。
- 完成前执行的相关测试、构建和质量检查。

停止条件：
- 需要新增权限、破坏兼容、执行数据清理或改变重大产品方向时暂停确认。
```

对简单、低风险任务可以压缩为几行，但目标、范围、验收标准和验证方式不能缺失。

## 3. 标准开发循环

### 3.1 发现

1. 检查工作区，区分用户已有改动和本轮改动。
2. 阅读 `AGENTS.md` 指定的基础文档和任务类型文档。
3. 搜索现有实现、测试和相似模式，不重复创建已有能力。
4. 根据真实代码确定最小改动范围，不能只依据文档声称。

### 3.2 契约

1. 写清输入、输出、权限、状态变化和错误语义。
2. 接口或数据库变化先核对对应设计文档。
3. 将相邻优化列为非本轮范围；若当前结构已妨碍安全实现，再单独安排结构整理。

### 3.3 Red

符合 `docs/development/testing.md`“必须新增测试”的行为改动，先增加或修改一个能够失败的聚焦测试：

1. 测试应描述用户可观察行为或业务约束，不绑定无关实现细节。
2. 运行该测试并确认失败原因与目标一致；编译错误、夹具错误或环境故障不算有效 Red。
3. 修复缺陷时，优先用能够复现缺陷的回归测试形成 Red。

如果无法可靠制造 Red，例如纯配置兼容、仅删除死代码或必须依赖不可用的外部环境，应在开发记录中说明原因和替代验证，不能声称执行了 TDD。

### 3.4 Green

1. 只实现让目标测试通过所需的最小完整方案。
2. 不用硬编码、绕过权限、弱化校验或吞掉异常换取绿灯。
3. 先运行聚焦测试，再运行受影响模块的相关测试。

### 3.5 Refactor

测试保持绿色后再整理结构：

1. 删除重复逻辑，使用现有分层和命名约定。
2. 如果修改让大 Service、Controller 或 Vue 页面继续明显膨胀，应检查能否提取独立职责；不能合理拆分时在总结中说明原因。
3. 不在功能提交中夹带与目标无关的大范围重构。
4. 重构后再次运行聚焦测试。

### 3.6 Verify

根据改动风险执行从小到大的验证：

1. 聚焦单元或组件测试。
2. 受影响模块测试。
3. 类型检查、静态分析和生产构建。
4. 涉及数据库真实约束时运行 Testcontainers。
5. 涉及跨层关键流程时运行 Playwright E2E 或最小浏览器验收。

覆盖率门槛用于防止整体基线倒退，不替代对新增行为的针对性断言。

### 3.7 Deliver

1. 检查 diff 是否只包含本轮范围。
2. 同步当前月份 changelog，以及本轮实际影响的接口、数据库、架构、测试、路线图或状态文档；不要机械更新无关文档。
3. 按 `docs/development/review-checklist.md` 自审。
4. 按 `docs/development/git-rules.md` 创建一次聚焦提交。
5. 汇报完成内容、修改文件、Red/Green 证据、完整验证、遗留风险和 commit。

## 4. TDD 适用边界

本项目采用“高风险行为强制测试先行，低风险改动按价值补测试”，不宣称所有改动都是严格 TDD。

必须优先执行 Red-Green-Refactor：

- 判分、考试、错题、权限、限流、事务和并发；
- 公共接口契约、数据库约束和迁移；
- 缺陷修复；
- 复杂前端状态、路由守卫、流式解析和安全过滤；
- AI 结构化输出解析、私有答案和真实完成事件。

通常可以不制造 Red：

- 纯样式、文案和无行为布局调整；
- 只更新文档；
- 无逻辑变化的机械重命名或格式化；
- 第三方工具生成且已有上层验证的代码。

例外不代表不验证。至少仍需执行与改动相称的构建、静态检查或浏览器检查。

---

## 5. 完成定义

一项开发任务只有同时满足以下条件才算完成：

- 用户可观察结果已经落地，不是计划、伪代码或长期假数据；
- 修改范围聚焦，未覆盖用户已有改动；
- 必须测试先行的行为有有效 Red 和 Green 证据，或明确记录合理例外；
- 相关测试、构建和质量门禁通过；
- 前后端、数据库和文档契约保持一致；
- 没有为了绿灯弱化业务规则；
- 风险、未执行验证和遗留问题已诚实说明；
- 相关文档已同步并完成聚焦提交。

---

## 6. 防止代码失控的审查问题

提交前逐项判断：

1. 是否创建了已有能力的第二套实现？
2. 业务规则是否被放进了 Controller、Vue 页面或临时工具函数？
3. 是否通过复制粘贴扩展了相似分支，而不是提取稳定职责？
4. 是否新增了无法解释的依赖、全局状态或隐式副作用？
5. 测试是否只验证 Mock 调用，而没有保护真实业务结果？
6. 是否把覆盖率数字、生成次数或按钮点击冒充业务正确性？
7. 文件继续膨胀时，是否记录了拆分判断和取舍？
8. 文档和真实代码是否一致？
