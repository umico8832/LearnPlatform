# 开发工作流

本文档维护任务拆分、开发循环、完成与阶段边界及审查标准。测试细则见[测试策略](testing.md)，
提交细则见[Git 规则](git-rules.md)，文档归属见[文档中心](../index.md#文档维护)。

## 任务边界

修改前检查工作区与真实实现，确定目标、范围、验收方式和提交边界。简单任务用几行说明即可，
不要求填写固定 Prompt 模板；能安全推断的实现选择直接推进，重大方向或授权冲突才询问用户。
涉及用户流程时，验收应覆盖真实前后端接口；后端独立完成或假数据页面不等于业务闭环完成。

用户交给的任务较大时，开工前先拆好并写进[任务单](collaboration.md#任务单)给用户看：分几块、每块做完是什么样、预计几个提交。
用户确认后再开始；中途发现需要多拆或少拆，就更新这份计划。

## 开发与验证

1. 搜索现有代码、测试和领域文档，明确输入输出、权限、状态变化及错误语义，复用已有能力。
2. 按[测试策略](testing.md#5-必须新增测试的情况)决定是否测试先行。有效 Red 必须因目标行为失败，
   编译错误、夹具错误或环境故障不算；无法形成 Red 时按测试策略记录例外与替代验证。
3. 完成满足验收的最小实现，运行聚焦验证；必要结构整理保持业务约束并复验，不夹带无关重构。
4. 按[文档维护](../index.md#文档维护)更新实际受影响的资料，自审 diff 后依照 Git 规则判断是否提交。
5. 整个任务做完后跑一次[完整检查](testing.md#2-验证分两档)；发现的问题按 Git 规则修复，同一目的的修复并入原提交。

纯文案、链接或无行为机械修改采用相称检查，不套用完整开发循环或制造失败测试。

### 运行环境与服务复用

- 日常开发默认采用[本地开发](../getting-started/local-development.md)：Docker 基础服务、本地前后端。
  验收前确认实际页面地址、服务所属工作目录和后端启动状态；端口可访问不等于运行的是当前工作区。
  可通过已有终端、进程工作目录或启动记录核对，不读取进程环境中的密钥。
- 优先复用用户已启动且对应当前工作区的服务；只补启动缺失的必要服务。前端普通改动使用热更新，
  后端代码或运行配置变化后只重启对应后端，不能用旧进程验证新代码。配置生效方式见本地开发指南。
- 普通页面检查、接口联调和局部测试不触发 `app-up`。需要验证镜像、Nginx、容器网络或明确要求
  完整 Docker 联调时，按 [Docker 开发](../getting-started/docker-development.md)准备环境；
  正式 E2E 使用[测试策略](testing.md#8-浏览器-e2e-环境)的隔离入口，不以日常数据库替代测试库。
- 重启前确认目标进程属于本项目并说明原因；不能因为端口占用而直接结束未知进程。任务结束时，
  保留用户原本运行的服务；本轮临时启动的服务按任务需要收尾，并说明保留或停止状态。
  不把 `down`、重建镜像或清理缓存作为普通开发任务的固定收尾步骤。

### 文档同步收尾

针对本次改动涉及的事实，完成前核对：

1. 哪些对外行为、业务约束或架构事实改变了，其完整定义属于哪份文档？归属按[文档中心](../index.md#权威来源)。
2. 哪些旧描述已失效，应替换、删除或改成引用？已完成的候选从 future 移出，不能只追加实现说明。
3. 是否又在第二处完整定义了同一事实？保留必要摘要与链接，消除重复细则。

只检查受影响文档及相关引用；未改变文档记录的事实时不要求文档 diff，也不因收尾检查扩展到全库文档整治。

## 审查标准

- 先确认审查对象与范围；只读审查不修改文件，没有读取实现时明确证据局限。
- 优先检查授权目标、真实业务结果、权限、判分、事务、数据隔离与架构边界；
  不以覆盖率、按钮点击或调用次数代替业务正确性和学习效果证据。
- 检查重复实现、无依据的依赖与副作用、大文件职责膨胀，以及遗漏的契约文档和必要验证。
  提交条件统一按[Git 规则](git-rules.md#4-commit-前检查)核对，不再维护第二份清单。
- 报告可定位的问题、影响和最小处理建议，区分阻塞问题与可选改进；无问题时不凑清单，
  不默认粘贴完整 diff。存在阻塞问题时明确不建议提交。

## 完成与交付

完成用户交给的整个任务、通过完整检查并按 Git 规则提交，就是任务完成；未跑完整检查时如实说明。
推送不是完成条件，只在用户要求时进行，推送前的检查见 [Git 规则](git-rules.md#5-revert检查点分支与推送)。

### 推送后 CI 失败

推送前已在本地跑过与 CI 相同的完整检查，CI 再失败说明本地与 CI 环境有差异或存在不稳定用例。
先读 CI 已有的证据：失败日志、Playwright 报告里的页面快照与 trace；再在本地复现并修复，同时把差异补进完整检查。
修好前不继续新的业务开发，除非已确认失败来自外部基础设施且无法通过仓库修改解决，此时记录事实和证据。

## 阶段边界

- 完成用户当前交给的任务就停，汇报结果；不因 status 或路线图还有下一步就自行继续。
- 阶段的完成标准写在[路线图](../product/roadmap.md)，数量有限、可客观判断；全部满足就结束。
  中途发现的优化记进任务单，不加进当前阶段。

## 交付汇报

有修改时报告结果、主要文件、验证与未执行项、剩余必需工作及提交状态。
高风险行为说明有效 Red/Green 或合理例外；下一步只列真实必需工作，不为填满模板创造任务。
只读问答和审查直接给出结论与证据，不套开发交付模板。
