# Agent Git 规则

本文档记录 LearnPlatform 项目中 AI Agent 处理 Git、commit、分支、回滚和历史操作时必须遵守的规则。适用于 Codex、Cline、Mimo、GPT 或其他 Agent。

---

## 1. 基本原则

- 项目默认在实现功能、修复问题、重构或文档规则变更完成后，由 Agent 在验证和文档同步后自动创建一次聚焦的本地 commit；用户只要求分析、审查、解释、调研、计划或建议 commit message 时不提交。
- 一个 commit 只对应一个可独立解释和回滚的变更目的。实现该目的所需的代码、测试、迁移和同步文档应放在同一个 commit 中，不应为了文件类型不同机械拆分。
- Agent 不允许在用户未明确授权时 push、force push、rebase、reset、清理历史、删除分支或 tag，也不得改写远端历史。
- 不要为了“工作区干净”删除、回滚、覆盖或夹带用户已有改动。
- 重大方向或破坏性操作未确认、Git 状态不确定、存在未解决冲突，或本轮引入的验证失败时，不自动 commit。

---

## 2. Commit 前检查

准备 commit 前必须确认：

- 本轮属于自动提交场景，或用户已经明确要求提交；
- 修改范围符合本轮用户要求；
- 必要测试、构建或文档检查已执行并通过；
- 相关文档已按实际影响同步；
- `git status` 和待提交 diff 中没有不应提交的文件或代码块；
- 未执行的非必要验证、存量失败、遗留问题和风险已在总结中说明。

禁止提交：

- `.env`；
- 真实 API Key、Token、Cookie、数据库密码或个人隐私数据；
- 本地 IDE 配置、机器私有配置；
- `node_modules/`、构建产物、缓存、日志；
- 与本轮任务无关的文件或代码块。

工作区存在其他未提交改动时：

- 能可靠按文件或代码块区分来源，且本轮暂存不会覆盖、依赖或夹带其他改动时，可以只 stage 本轮改动；
- 同一文件存在交叉修改、改动来源不明、无法可靠拆分，或本轮改动依赖未提交的其他改动时，不自动 commit，并向用户说明阻塞范围；
- 禁止使用回滚、清理或覆盖命令把其他改动移出工作区。

---

## 3. 验证失败与检查点提交

- 本轮引入的测试、构建、静态检查或文档检查失败时，禁止把任务作为完成结果自动提交；说明风险不能替代修复。
- 已确认属于存量问题，且有证据表明本轮没有新增或扩大失败时，可以提交，但必须在交付总结和开发日志中记录失败命令、原因与影响范围。
- 环境不可用导致非必要验证无法执行时，应运行可用的替代验证并说明缺口；高风险行为缺少必要验证时仍不得作为完成结果提交。
- 只有用户明确要求保存未完成状态时才允许检查点提交。检查点不得声称任务完成，commit message 应使用 `chore(checkpoint): <中文说明>`。

---

## 4. Commit Message 规范

格式：

```text
<type>(<可选作用域>): <中文简短描述>

<可选：详细说明>
<可选：Closes #42>
```

大多数提交一行即可。`type` 只能使用：

- `feat`：新功能
- `fix`：修 bug
- `docs`：文档
- `style`：代码格式，不影响逻辑
- `refactor`：重构
- `perf`：性能优化
- `test`：测试
- `chore`：构建、工具、依赖和明确授权的检查点
- `ci`：CI/CD
- `security`：安全

要求：

- 提交主题必须使用中文描述；
- 修改涉及特定模块时优先添加作用域；
- 禁止使用 `fix bug`、`wip`、`修改了一些文件`；
- 禁止写成 `feat: 添加A顺便修了B` 这类混合事项描述；
- CI 使用 `scripts/check-commit-messages.py` 校验新增的非合并提交；自动生成的 merge commit 不受主题格式限制。

示例：

```text
feat(auth): 完成 JWT 登录注册流程
```

```text
docs(roadmap): 更新项目阶段进度
```

```text
fix(question): 修复题目选项保存失败问题
```

---

## 5. 分支与远端操作

- 当前采用单主分支模型，`main` 是唯一长期分支。聚焦、已验证的本地改动可以直接 commit 到本地 `main`，但不得据此自动 push。
- 用户要求并行开发、实验性改动、隔离高风险改动或使用 PR 时，再创建短期分支；创建前确认当前分支和工作区状态，Agent 分支默认使用 `codex/` 前缀。
- 用户已明确要求某项 merge、cherry-pick 或 revert，且目标和影响范围清楚时，可以按该授权执行；否则应先说明影响并等待确认。
- `git reset --hard`、`git clean`、`push --force`、删除分支、删除 tag 和其他历史改写操作必须获得用户对具体目标的明确确认。
- 如果用户只要求给出建议 commit message，不要实际 commit。

---

## 6. 冲突与异常处理

- 遇到 merge、rebase 或 cherry-pick conflict 时，先说明冲突文件和冲突性质，不要随意选择一边覆盖。
- 发现工作区中有用户改动时，应保留并绕开；如果影响本轮任务，先说明情况再继续。
- 命令失败时先分析原因，不要盲目重复执行同一个失败命令。
