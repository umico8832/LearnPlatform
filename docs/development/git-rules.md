# Agent Git 规则

本文档定义 LearnPlatform 的提交、分支和远端操作规则。格式兼容
[Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)，并采用
[Pro Git](https://git-scm.com/book/en/v2/Distributed-Git-Contributing-to-a-Project)
关于逻辑独立提交、简短主题和正文解释动机的原则。

## 1. 基本原则

- 一个 commit 只对应一个达到预定验收边界、可独立解释、验证和回滚的模块或业务闭环。
- 同一目的所需的代码、测试、迁移和文档共同提交，不按文件类型机械拆分。
- 无关重构、独立依赖升级、纯格式化和不同业务结果应拆成不同提交。
- 开发过程默认允许保留未提交改动；一次对话、一次 Red/Green、一个子任务或一次验证结束后不得
  自动提交。
- 提交到 `main` 的每个 commit 都应处于完整状态，不包含 WIP、占位实现或已知编译失败。
- 只有完成预先定义的模块/阶段验收、完成可独立发布的缺陷或安全修复，或用户明确要求提交时，
  Agent 才创建本地提交。
- 本地 commit 不授权 push、rebase、force push、reset、删除分支或 tag。

### 提交粒度

提交的最小单位是一个达到预定范围的模块、阶段或完整业务闭环，而不是一个文件、一个函数、一个
原子知识名词或 Agent 当前刚完成的子任务。开始开发前应在任务契约中写明本批次的提交边界；未达到
该边界时，即使代码、测试和文档均已通过，也只报告进度并继续保留未提交改动。

- 同一主题下连续迁入的 Tutor 内容、知识切片、课件、理解检查、迁移、测试和必要文档应累计到
  预定模块完成后一起提交。例如 ArrayQueue 的表示、入队、出队、容量调整与复杂度共同组成一个
  学习模块，不得按单个知识切片逐一提交。
- 单条 Flyway 迁移、单个组件、单个接口、单次样式调整、单份文档同步或单轮测试通过，均不能单独
  证明达到提交边界。
- 允许单独提交的例外仅限：可独立发布的缺陷修复、安全修复、紧急回滚、明确的兼容性修复，或用户
  明确指定的提交范围。公共接口或数据库变化本身不自动构成例外；若属于同一模块仍应与模块合并。
- 一次提交不得混合无关课程、不同学科、独立缺陷修复或大规模重构。提交过大时按预先声明的模块
  边界拆分，不得退回到逐个微小切片提交。
- 未达到提交边界而需要停止时，默认保留工作区改动并报告剩余范围；只有用户明确要求保存中间状态
  时才允许创建检查点提交。

## 2. Commit Message

格式：

```text
<type>(<optional-scope>)<optional-!>: <中文简短描述>

<可选或按规则必需的正文>

<可选 footer>
```

### Type

| Type | 用途 |
|---|---|
| `feat` | 新增或扩展用户、管理员或调用方可观察的能力 |
| `fix` | 修复错误行为、错误数据或失败流程 |
| `docs` | 只修改文档、注释或示例 |
| `style` | CSS、主题、布局、视觉呈现或纯格式调整，不改变业务规则 |
| `refactor` | 调整代码结构但不改变外部行为 |
| `perf` | 保持行为一致的性能优化 |
| `test` | 只修改测试、夹具或测试基础设施 |
| `build` | 依赖、Maven、npm、Vite、Dockerfile、打包和构建配置 |
| `ci` | CI/CD 工作流和发布自动化 |
| `security` | 不适合归入普通 `fix` 的独立安全加固 |
| `chore` | 无法归入以上类型的仓库维护或授权检查点 |
| `revert` | 撤销明确的历史提交 |

用户可观察的新能力使用 `feat`，即使同时包含前端、后端和数据库修改。UI 视觉变化
使用 `style`，交互行为变化使用 `feat` 或 `fix`。依赖和构建变化优先使用 `build`，
不要用 `chore` 包装无法概括的大杂烩提交。

### Scope

Scope 描述一个主要业务域或技术域。推荐使用：

```text
auth catalog course learning tutor paper question practice review exam
submission admin ai visualization product frontend backend database security
docs build ci git agent project deps
```

- scope 可省略，有明确领域时优先填写；
- 只允许小写字母、数字和连字符，例如 `course-store`；
- 一个提交只能有一个 scope，禁止 `backend,frontend` 或 `api+ui`；
- 跨层实现同一业务能力时使用业务 scope，例如 `feat(submission)`；
- 推荐列表无法覆盖新领域时可以使用语义明确的 kebab-case scope。

### 主题

- 使用中文描述结果，代码标识可以保留英文；
- 推荐不超过 50 个字符，硬上限为 72 个字符；
- 不以句号、分号或感叹号结尾；
- 不写测试数量、完整文件清单、阶段日志或多个并列目的；
- 不使用 `fix bug`、`update`、`WIP`、`修改了一些文件` 等空泛描述。

## 3. 正文与 Footer

小范围、目的和影响明显的提交可以只有一行，例如：

```text
docs(readme): 修正本地启动命令
style(auth): 调整登录页移动端间距
fix(search): 修复空关键词重复请求
```

出现以下任一情况时必须写正文：

- 修改公共 API、数据库迁移或数据兼容；
- 修改鉴权、权限、判分、考试、事务、并发或隐私边界；
- 同时修改多个运行层或多个应用；
- 引入、替代或撤销架构与产品决策；
- 存在非显而易见的动机、取舍、兼容影响或降级行为；
- 包含破坏性变更、存量失败、验证缺口或需要交接的遗留风险。

正文简要说明动机、关键变化、不变量、验证和兼容影响，不复制完整 changelog。正文按
“最终结果”组织，不按修改文件组织；`Round N` 只属于 changelog，不得写入 Commit Message。

除只有一行即可说明的小型提交外，正文统一使用项目符号，不使用连续自然段描述多个变更点：

- 默认使用 2～4 个结果级项目符号，优先描述业务行为、工程规则或可观察结果；
- 不使用 `testing.md: ...`、`workflow.md: ...`、`SomeService.java: ...` 等逐文件清单作为正文结构；
- 能合并表达的实现细节应压缩，不把交付报告、diff 清单或 changelog 原样搬进 commit；
- 每个项目符号只表达一个主要结果，避免一个 bullet 塞入多个无关并列事项。

存在验证内容时统一使用以下排版：

```text
<type>(<scope>): <中文简短描述>

- <关键变化 1>
- <关键变化 2>
- <关键变化 3>

验证：

- <验证项 1>
- <验证项 2>
```

标题、正文和 `验证：` 区块之间保留一个空行；`验证：` 后也保留一个空行。需要单独说明
兼容性、迁移或风险时，可以使用 `兼容性：`、`迁移：`、`风险：`，排版规则与 `验证：` 相同。

```text
feat(paper): 建立试卷学习模式

- 保留原始试卷结构并增加逐题学习状态
- 原题作答与 AI 教学写入同一课程记录

验证：

- mvn test -Dtest=PaperStudyServiceTest
- npm run test -- PaperStudyView
```

常用 footer：

```text
Refs: #123
Closes: #123
Co-authored-by: Name <email@example.com>
```

破坏性变更必须同时在主题中使用 `!`，并用 `BREAKING CHANGE:` 说明迁移影响：

```text
feat(learning)!: 统一课程学习状态契约

- 统一课程学习事件接口并删除旧契约

BREAKING CHANGE: 客户端必须改用新的学习事件接口。
```

向后兼容的 Flyway 迁移不自动等于破坏性变更。

## 4. Commit 前检查

提交前确认：

- 修改范围符合用户要求，暂存区只包含本提交需要的文件或代码块；
- 没有 `.env`、密钥、Token、Cookie、密码、隐私数据、本机配置、缓存、日志或构建产物；
- 必要测试、构建、静态检查或文档检查已通过；
- 接口、数据库、架构、状态和开发日志只按实际影响更新；
- Commit Message 正确，复杂提交的正文包含必要信息。

工作区存在其他改动时，只有能够可靠隔离且本提交不覆盖、不依赖、不夹带这些改动，
才能只暂存本轮范围。无法区分来源或同一文件交叉修改时不自动提交，也不得通过回滚、
清理或覆盖移走用户改动。

本轮引入的必要验证失败时不得作为完成结果提交。确认属于存量问题且本轮没有扩大时，
可以提交，但必须在正文、开发日志和交付总结中记录失败命令与影响。高风险行为缺少
必要验证时不能用风险说明代替验证。

## 5. Revert、检查点与分支

撤销提交使用：

```text
revert(auth): 撤销认证页主题调整

- 移动端对比度回归尚未解决

Reverts: <commit-sha>
```

只有用户明确要求保存未完成状态时才允许：

```text
chore(checkpoint): 保存课程状态迁移中间结果
```

检查点正文必须说明未完成内容、已知失败和恢复方式，不能作为任务完成结果。

`main` 是唯一长期分支。低风险、聚焦且已验证的本地变化可以直接提交到本地 `main`；
多提交功能、实验性改动、高风险迁移、并行开发或需要 PR 审查时使用 `codex/` 前缀
短期分支。

未经用户对具体目标明确授权，不执行 push、force push、rebase、reset、清理历史、
删除分支或 tag。禁止对共享分支 force push。

## 6. 自动检查

CI 使用 `scripts/check-commit-messages.py` 检查新增的非合并提交：

- type 是否允许；
- scope 是否为单个小写 kebab-case；
- 主题是否包含中文、超过 72 个字符或使用禁止的结尾标点；
- `!` 与 `BREAKING CHANGE:` 是否成对出现；
- 正文是否包含禁止的 `Round N` 行或未使用项目符号的独立自然段；
- `验证：`、`兼容性：`、`迁移：`、`风险：` 等区块前后是否保留规定空行。

校验范围由 push 事件的 `before`/HEAD 决定。用户明确授权的历史重写（amend、rebase、
force push）后，旧 `before` SHA 可能不再可达：此时 CI 通过 push 事件显式传入
`FORCED_PUSH`，脚本对不可达基线只输出警告并校验当前 HEAD 提交，不检查整个仓库
历史，也不让无关旧提交阻塞 CI；普通 push 的不可达基线仍视为异常并明确失败。

自动检查不能判断提交是否真正原子，也不能可靠判断正文是否按“结果”而不是“文件”组织；
提交者和审查者仍需人工检查提交边界与信息密度。Merge commit 不受主题格式校验。
