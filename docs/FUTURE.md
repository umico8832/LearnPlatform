# AI 驱动的题目学习平台 - 后续扩展方向

本文档只记录尚未完成的候选方向和优先级。已交付能力以 `docs/ROADMAP.md`、`docs/HANDOFF.md` 和代码为准，不在此重复列为待办。

---

## 当前判断

项目已具备刷题、错题、考试、AI 讲解、学习诊断、投稿审核、间隔复习、搜索和 AI 调用总览等业务底座。近期不应继续横向扩展功能，而应先完成演示验收，并把 AI 从“可调用”提升为“可治理、可评估”。

## P0：演示与质量收尾

- 补齐考试完整作答、提交和结果查看的浏览器验收。
- 根据 `docs/DEMO.md` 产出用户端和管理端真实截图。
- 推送后确认 GitHub Actions 的后端、前端和 Docker Job 实际通过。
- 为登录、刷题、错题复习、考试和管理端审核增加少量高价值端到端测试。
- 解决或明确记录本地 Testcontainers 与 JDK/Docker Socket 的兼容性方案。
- 将 Redis 缓存 TTL 从 `RedisConfig` 硬编码值迁移到应用配置。

## P1：AI 运营治理

### 真实成本与可观测性

- 从 AI 上游响应提取真实 token 用量；当前字段存在，但不能作为真实成本依据。
- 根据模型单价估算输入/输出成本，按功能、模型、用户和时间聚合展示。
- 生成调用日报/周报，提示失败率、异常用量和成本突增。
- 记录 Prompt/模型版本，支持将调用效果、失败原因与配置版本关联分析。

### 用户级控制

- 支持管理员为用户设置独立 AI 配额、有效期和调整原因。
- 区分低成本与高成本功能的配额或限流策略。
- 明确配额耗尽、上游故障和 AI 未配置时的用户端降级体验。

## P2：内容质量与学习效果闭环

### 内容治理

- 缓存投稿复审结果，并保留复审结论的时间与依据。
- 做重复题/高度相似题检测，先使用可解释的规则和已有元数据，数据规模足够时再评估向量检索。
- 为题目建立版本、纠错、下线和审核记录，确保 AI 辅助不绕过人工确认。

### 学习效果

- 定义 AI 讲解查看率、变式训练完成率、复习按时率、同知识点后续正确率等指标。
- 在学习报告和管理端区分“使用了 AI”与“学习效果提升”，避免只优化调用量。
- 依据真实效果数据再调整推荐策略、学习路径和讲解样式。

## P3：长期候选

- 多租户/班级与教师布置作业、考试。
- 微信小程序或移动端应用。
- PDF、Word、图片解析与 OCR。
- 爬虫或外部内容整理。
- 用户上传题库自动入库。
- 语音交互。
- 多模型路由与复杂推荐系统。

这些方向需要在数据规模、合规边界、运维能力和真实用户需求明确后再排期。题目自动发布、标准答案修改等关键操作始终保留管理员确认。

## 排期原则

1. 先完成 P0，形成可信的演示与质量基线。
2. P1 优先选择 AI 成本与配额治理，而不是增加新的 AI 展示功能。
3. P2 以内容可信度和学习效果为准绳；向量推荐不是默认必做项。
4. 新能力确定具体接口、数据模型和边界后，再更新 `API_DESIGN.md`、`DB_DESIGN.md` 与 `ARCHITECTURE.md`。
